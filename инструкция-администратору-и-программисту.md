# Интеграция LitePMS → Bitrix24: инструкции

Документ описывает финальную версию интеграции (вебхук `litepms-webhook.php` + конфиг `config.php`).
Предназначен для двух аудиторий:

- **Часть 1 — администратору** (кто разворачивает и настраивает систему, устраняет ошибки).
- **Часть 2 — программисту** (кто развивает код и разбирается во внутреннем устройстве).

Сопроводительные файлы: `config (9).php.txt` и `litepms-webhook-fixed.php.txt`.

---

# Часть 1. Инструкция администратору

## 1.1. Что делает интеграция

Вебхук принимает события (брони) из системы LitePMS, сопоставляет их с **гостем**, хранит
всю историю бронирований гостя и передаёт данные в **Bitrix24** и аналитику **Roistat**.

Схема по умолчанию — **одна карточка на бронь**, привязанная к посетителю (гостю):

- каждый **лид** и (при правке брони) **сделка** фиксируют данные конкретной брони:
  номер, заезд/выезд, гостей, сумму, оплату, статус, историю;
- к лиду и сделке привязан единый **контакт гостя** (ищется по телефону/почте, при
  отсутствии — создаётся), в котором копится история всех бронирований гостя;
- статус и оплата отражаются и на лиде, и на сделке — для сквозной аналитики Roistat.

## 1.2. Из чего состоит интеграция

Интеграция состоит из двух файлов и, как правило, небольшой настройки в портале Bitrix24:

| Файл | Куда кладётся | Что делает |
|------|--------------|------------|
| `litepms-webhook.php` | **в webroot** сайта (доступен по URL для LitePMS) | обрабатывает вебхуки LitePMS |
| `config.php` | **вне webroot** (не в git, не по URL) | все настройки: ключи, поля, воронки, флаги |

В вебхуке путь к конфигу задаётся константой `$configFile`
(в текущей версии: `/home/avshotelru/avshotel.ru/src/config.php`).

## 1.3. Установка

1. Положите `litepms-webhook.php` в webroot сайта, чтобы у него был публичный URL
   (например, `https://site.ru/litepms-webhook.php`).
2. Положите `config.php` **вне** webroot (например,`/home/user/src/config.php`) и укажите
   его путь в `$configFile` в начале вебхука.
3. В настройках LitePMS укажите URL вебхука как адрес приёмника событий (new/edit/payment/delete).
4. Выполните настройку портала Bitrix24 (раздел 1.4) и конфига (раздел 1.5).
5. Проверьте работоспособность (раздел 1.6).

## 1.4. Настройка портала Bitrix24 (один раз)

### 1.4.1. Вебхук Bitrix24

В `config.php` сохраняется адрес входящего вебхука:

```php
'bitrix_webhook_url' => 'https://contact-center.bitrix24.ru/rest/1183/***************/',
```

- Вебхук должен иметь права на работу с **лидами, сделками и контактами** (чтение и запись).
- Адрес берётся в портале: *Разработчикам → Другое → Входящие вебхуки → Добавить*.

### 1.4.2. Ответственный за брони

Все лиды (и обновления) назначаются на конкретного пользователя — `responsible_user_id`.
В текущей настройке это **«Администратор БО Энергетик» (id 16083)**:

```php
'responsible_user_id' => 16083,
```

Если убрать это поле, лид назначается на пользователя, под чьим токеном работает вебхук
(по умолчанию 1183).

### 1.4.3. Воронка сделок (категория 39)

Сделки создаются в воронке **«ТК Энергетик B2C»** (ID категории 39). Этапы, которые
использует интеграция:

```php
'deal_fields' => [
    'category_id' => 39,
    'stage_new'   => 'C39:NEW',    // этап при создании сделки
    'stage_paid'  => 'C39:WON',    // полная оплата → «Сделка успешна»
    'stage_cancelled' => 'C39:LOSE', // отмена брони → «Сделка провалена»
],
```

Этапы `stage_paid` / `stage_cancelled` — **по желанию**: если их убрать, при оплате/отмене
обновляются только данные и оплата, а этап сделки не трогается.

### 1.4.4. Пользовательские поля (UF)

Интеграция использует пользовательские поля на **лидах** и **сделках**. Ключи полей
указываются в `fields` (лид) и `deal_fields` (сделка). Пример значений из текущей настройки:

**Лиды (`fields`):**

|------------|-----------|

| Номер брони LitePMS | `ufCrm_1790163998` |
| Roistat Order ID | `ufCrm_1790328481` |
| roistat-визит | `ufCrmRoistat` |
| yclid | `ufCrm_1790232672` |
| ym_clid | `ufCrm_1790232703` |
| etext | `ufCrm_1790232726` |
| widget_id (service_id) | `ufCrm_1790577819` |

**Сделки (`deal_fields`):**

**Важно:** если в вашем портале коды полей отличаются (поля пересоздавались), их нужно
поправить в конфиге под фактические коды из портала (*Настройки → Поля → Сделки/Лиды*).

## 1.5. Настройка конфига

### 1.5.1. Ключи Roistat

Используются **два разных ключа**:

```php
// Ключ для интеграции — для ПРОКСИЛИДА (Интеграции → Bitrix24 → показать)
'roistat_integration_key' => '*************',

// API-ключ проекта — для СТАТУСОВ и других методов
'roistat_api_key' => '************',

'roistat_project_id' => '47226',
```

### 1.5.2. Как Roistat получает статус

Статус в аналитике Roistat **берётся из карточки CRM** (интеграция Roistat читает статус
сделки/лида в Bitrix24). Поэтому тянуть статус отдельным API-вызовом `status/update`
**не нужно**.

Для этого у создания брони стоит флаг `is_skip_sending => '1'`: Roistat принимает аналитику
(атрибуцию визита), но **не создаёт** собственную карточку в CRM. Итог — на броню остаётся
**одна карточка** (та, что создаёт вебхук).

### 1.5.3. Маппинг статусов брони → статус лида

```php
'lead_status_map' => [
    1 => 'NEW',        // не подтверждено → лид создан
    2 => 'IN_PROCESS', // подтверждено   → в работе
    3 => 'JUNK',       // отменено       → некачественный лид
    4 => 'IN_PROCESS', // выезд (оплачено) → в работе
    5 => 'JUNK',       // незаезд        → некачественный лид
    6 => 'PROCESSED',  // проживание, полная оплата → обработан
    8 => 'IN_PROCESS', // резерв         → в работе
    9 => 'IN_PROCESS', // overbooking    → в работе
],
```

При необходимости статус 6 можно поменять на `CONVERTED` («Качественный лид»).

### 1.5.4. Создание записей оплаты на сделке

```php
'create_payments' => true,
```

- `true` — при `payed > 0` на сделке создаётся реальная запись оплаты (блок «Оплата и
  доставка») без дубликатов; оплаченная сумма видна в сквозной аналитике.
- `false` — оплата только пишется в пользовательское поле (прежнее поведение).

### 1.5.5. Режим отладки

```php
'dry_run' => false,
```

- `false` — реальная работа.
- `true` — вебхук логирует «DRY RUN: would create lead» и **ничего не создаёт/не меняет**
  в портале. Удобно для проверки приёма событий без изменений данных.

### 1.5.6. Логи

```php
'log_file' => '/home/avshotelru/avshotel.ru/src/litepms-logs/litepms-webhook.log',
```

Дополнительные журналы (необязательные, выводятся по умолчанию рядом с основным):

- `<log_file>.debug` — подробный уровень (`log_level`);
- `<log_file>.error` — только ошибки;
- `<log_file>.duplicates` — пропущенные повторы событий;
- `<log_file>.processed` — хеши уже обработанных событий (защита от дублей).

## 1.6. Проверка после установки

1. Зайдите в портал и откройте раздел **Ленты вебхуков / журнал событий** (или логи
   сервера) — после боевого события LitePMS в логе должны появиться строки
   `IN [PARSED] type=... booking_id=...` и `[DONE] type=... status=success`.
2. Создайте/измените бронь в LitePMS и убедитесь, что в Bitrix24 появился **лид**,
   привязанный к **контакту гостя**, с заполненными полями (номер, даты, сумма, статус,
   история).
3. Проверьте, что при **правке брони** обновилась **сделка**: номер, гости, суммы, статус,
   оплата и история перенесены.
4. Убедитесь, что в **контакте гостя** копится история (`[...] booking_id=... room=...`).

## 1.7. Что делать при типовых проблемах

| Симптом | Действие |
|---------|----------|
| Тип события с новым именем не обрабатывается | В логе `UNHANDLED EVENT: <type>`. Проверьте, какое событие шлёт LitePMS, и добавьте его в обработчик (Часть 2). |
| Лид не создаётся | Проверьте `dry_run` (должен быть `false`), URL вебхука и права на лиды. |
| Дубли карточек | Проверьте журнал `.duplicates`: защита от дублей хеширует событие и пропускает повтор. |
| Сделка не появляется | Сделка создаётся/обновляется при правке брони (`edit_booking`). Убедитесь, что событие правки приходит. |
| Нет истории гостя | Проверьте `booking_history` в `fields`/`deal_fields` и `contact_fields` (если история гостя нужна в контакте). |

# Часть 2. Инструкция программисту

## 2.1. Структура и запуск

Вебхук:

1. **Сразу** отдаёт HTTP 200 (`OK`) и `fastcgi_finish_request()`, чтобы не держать LitePMS;
2. загружает конфиг из файла вне webroot;
3. читает `php://input`, разбирает через `parse_str($rawData, $data)`;
4. вычисляет хеш события и проверяет защиту от дублей (`*.processed`);
5. выполняет `switch ($eventType)` и пишет итог в лог.

## 2.2. Обрабатываемые события

| Событие (`type`) | Поведение |
|------------------|-----------|
| `new_booking`, `booking_module`, `channel_manager_booking`, `booking_module_request` | Создание брони: создаёт лид (или обновляет существующий) |
| `edit_booking` | Правка брони: обновляет лид и переносит данные на сделку |
| `booking_module_payment` | Оплата: обновляет только оплату (и статус при полной оплате), сделку не создаёт |
| `delete_booking` | Отмена: `status_id` принудительно ставится 3, лид/сделка обновляются |
| любое другое | `UNHANDLED EVENT: <type>` — пропуск |

**Ключевое правило:** ветки `edit_booking` / `delete_booking` / `booking_module_payment`
**не создают** лид. Если по брони лид не найден — событие фиксируется в журнале и
пропускается.

## 2.3. Поиск лида (сопоставление)

Приоритет поиска существующего лида:

1. по `booking_id` (поле `fields.booking_id`);
2. по `user_booking_id` (поле `fields.user_booking_id`);
3. по телефону гостя (`findLeadByPhone`) — если телефон есть в данных.

Это позволяет не плодить дубли: новая броня того же гостя (или повторное событие) находит
уже созданный лид и обновляет его (`LEAD ALREADY EXISTS ... → lead #id`).

## 2.4. Защита от дублей

```php
$eventHashSource = $eventType . '|' . $bookingId . '|' . ...;
$eventHash = hash('sha256', $eventHashSource);
```

- Для `edit_booking` в хеш входят `last_update`, `status_id`, `payed`.
- Для `booking_module_payment` — `invoice_id`, `price`.
- Для прочих — `date`.
- Уже обработанные хеши хранятся в `<log_file>.processed`; повтор события
  (`isEventProcessed`) пишется в `.duplicates` и пропускается.

Чтобы события вновь стали приниматься (например, после исправления), файл `.processed`
следует очистить/удалить.

## 2.5. Карточка гостя (контакт)

Функции: `findGuestContact`, `createGuestContact`, `ensureGuestContact`, `linkLeadToContact`,
`appendGuestContactHistory`.

- Контакт ищется по телефону/почте (`sanitizePhone`, `sanitizeEmail`);
- при отсутствии — создаётся и привязывается к лиду и сделке;
- история брони дописывается в контакт, только если в конфиге объявлен ключ
  `contact_fields => ['booking_history' => 'UF_CRM_...']` (в текущей версии конфига поля
  нет — история гостя копится в поле `booking_history` на лиде/сделке).

> **Внимание:** в финальном `config (9).php.txt` ключ `contact_fields` **не объявлен**,
> поэтому история в карточку самого контакта не дописывается. Чтобы включить — добавьте
> блок `contact_fields` c кодом поля истории на контактах.

## 2.6. Работа со сделкой (воронка 39)

При `edit_booking` все значимые данные брони переносятся на сделку того же визита Roistat
(`updateDealFromBooking`, `syncDealFromLead`):

- номер, гости, заезд/выезд, сумма, оплата, история, roistat-визит;
- сделка ищется по roistat-визиту (`findDealByBooking`);
- при полной оплате сделка может быть переведена на `stage_paid` (`C39:WON`), при отмене —
  на `stage_cancelled` (`C39:LOSE`);
- реальная запись оплаты создаётся только при `deal_fields.create_payments => true`.

## 2.7. Ответственный за лид

Функция `assignResponsible(array &$fields, array $config)`:

```php
if (!empty($config['responsible_user_id'])) {
    $fields['ASSIGNED_BY_ID'] = (int)$config['responsible_user_id'];
}
```

Вызывается во всех путях записи (создание, правка, оплата). Если ключ убрать — лид
назначается на пользователя токена (1183).

## 2.9. Необязательные ключи конфига

Вебхук читает ряд ключей с дефолтами (`??`), их **можно** добавить в конфиг:

- `log_file_debug`, `log_file_error`, `log_file_duplicates`, `log_level`, `log_unmask_pii` —
  тонкая настройка журналов;
- `skip_old_bookings` — фильтр старых броней (`enabled`, `safety_statuses`,
  `skip_past_checkout`, `past_checkout_grace_days`, `skip_old_update_days`);
- `contact_fields` — история гостя в контакте;
- `paid_rule_exclude_statuses` — статусы, исключаемые из правил оплаты.

## 2.10. Разработка и тестирование

- Тестовые события отправляйте с `dry_run => true`, чтобы ничего не менять в портале.
- Следите за логами: строка `IN [PARSED]` → обработка → `[DONE] status=success|failed`.
- После изменения логики сопоставления/дублей очистите `.processed`, иначе прежние события
  будут пропущены.
- Код рассчитан на среду без сетевого доступа из песочницы разработки: боевые вызовы идут
  только через сервер, где развёрнут вебхук.
