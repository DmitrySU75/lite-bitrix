# План внедрения: Битрикс24 + Roistat (сквозная аналитика)

Портал: `contact-center.bitrix24.ru` · Проект Roistat: `47226` · Автор плана: Дмитрий Суменков

Цель плана — включить **все** возможности обеих систем без двойных карточек и двойной
отправки данных: Битрикс24 остаётся операционной системой (бронь, сделка, оплата, статус,
менеджер, автоматизация), Roistat — аналитической (атрибуция визита, источник/канал/ключ,
ROI/ROMI, воронка, товарная аналитика).

---

## 1. Роли систем (что какая делает)

| Система | Роль | «Единый источник правды» |
|---|---|---|
| **Битрикс24** | Операционная / бизнес | Данные брони, лид → сделка, сумма, оплата, статус, менеджер, автоматизация |
| **Roistat** | Аналитическая / маркетинг | Атрибуция визита, канал/источник/ключ, ROI/ROMI, воронка, товарная аналитика |

Ключевое правило: **бизнес-данные живут в Битрикс24, маркетинговая аналитика вычисляется
в Roistat из этих данных через нативную интеграцию.** Скрипт больше **не** отправляет
данные в Roistat сам.

---

## 2. Итоговая логика работы (как должно быть после внедрения)

```
Бронь (LitePMS) → вебхук litepms-webhook.php → Лид в Битрикс24
                     (данные брони + поле визита ufCrmRoistat)
                                          │
                         [нативная интеграция Roistat ↔ Битрикс24]
                                          │
                        Атрибуция визита → источник / канал / ключ
                                          │
            Менеджер: Лид → Сделка «Создать на основании»
                       (OPPORTUNITY = сумма, ведётся воронка)
                                          │
                 Статус «Продажа» / «Отказ» → Roistat закрывает визит
                                          │
            ROI/ROMI по каналам, товарная аналитика, модели атрибуции
```

---

## 3. Подготовка (Фаза 0) — проверить то, что уже есть

Ничего не меняем — только сверяем исходное состояние. Это снижает риск.

1. Открыть актуальный `litepms-webhook.php` (у вас — версия 32.0) и убедиться, что
   создание лида записывает поле визита: в `buildBookingFields()` строка
   `$result[$fields['roistat']] = ...` кладёт `ufCrmRoistat` — по нему Roistat свяжет
   карточку с визитом. **Это работает уже сейчас и менять не нужно.**
2. Сверить `config.php` (v15.0): поля `fields` должны соответствовать UФ-полям CRM.
   Полезный маппинг (используется и в настройке интеграции Roistat):

   | Смысл | Поле в Битрикс24 |
   |---|---|
   | Номер визита Roistat | `ufCrmRoistat` |
   | ID брони LitePMS | `ufCrm_1790163178` |
   | Номер брони LitePMS | `ufCrm_1790163998` |
   | Roistat Order ID | `ufCrm_1790328481` |
   | Заезд / Выезд | `ufCrmArrival` / `ufCrmDeparture` |
   | Номер (комната) | `ufCrmRoom` |
   | Гости | `ufCrmGuests` |
   | Стоимость брони | `ufCrmAmount` (+ `OPPORTUNITY` / «Сумма») |
   | Оплачено | `ufCrmPaymentAmount` |
   | История брони | `ufCrmBookingHistory` |

3. Зафиксировать текущий смысл статусов (из `lead_status_map`) — он переносится в
   настройку интеграции Roistat: `NEW` → в работе, `IN_PROCESS` → в работе,
   `PROCESSED` → «Продажа» (доход), `JUNK` → «Отказ» (нет дохода), `CONVERTED` — лид
   переведён в сделку (доход тогда берётся из сделки).

> Если на этом шаге что-то не совпадает (поля нет / поле пустое) — остановиться и
> исправить до перехода к Фазе 1.

## 4. Фаза 1 — отключить прокси-отправку в Roistat из скрипта

Файл: `litepms-webhook.php` (подготовленная версия приложена: `litepms-webhook.php`).

**Что делаем:**
1. В `createLeadFromBooking()` удаляем вызов:
   ```php
   maybeSendProxyLead($data, $config, $logFile, $maxLogSize);
   ```
   В подготовленном файле на его месте стоит поясняющий комментарий.
2. Удаляем функции `maybeSendProxyLead()` и `sendProxyLead()` целиком (в подготовленном
   файле уже удалены).
3. **Оставляем** в скрипте (не трогаем):
   - создание лида и всех полей брони;
   - запись `ufCrmRoistat` (номер визита) — это основа нативной атрибуции;
   - контакт гостя и историю броней;
   - запись статуса лида по `lead_status_map` (если реализована на обновлениях).

**В `config.php` менять ничего не нужно:** `roistat_send` / `is_skip_sending` /
`roistat_proxy_url` становятся неактивными (прокси больше не вызывается). Их можно
оставить или закомментировать — на работу не влияет. Не удаляйте `roistat_integration_key`
и `roistat_api_key` до окончательного переключения (могут пригодиться для диагностики).

**Деплой:** заменить файл на сервере, очистить/переименовать текущий лог
(`litepms-webhook.log`) для чистого прогона тестов, проверить, что PHP не падает.

---

## 5. Фаза 2 — включить нативную интеграцию Roistat ↔ Битрикс24

Выполняется в панели Roistat (не в Битрикс24 и не в скрипте):

1. Панель Roistat → **Настройки → Интеграции**.
2. Выбрать интеграцию **«1С-Битрикс / Bitrix24 (Лиды и сделки)»**.
3. Авторизовать портал `contact-center.bitrix24.ru`. Roistat сам создаст свой вебхук в
   Битрикс24 — это отдельно от `roistat_integration_key` из `config.php` (тот ключ
   использовался только для прокси скрипта).
4. Выбрать **объект, по которому считать доход**. Рекомендация: **сделки** (см. Фазу 3).
5. Настроить **сопоставление статусов** (Фаза 3, п.1).
6. Указать **поле суммы** (Фаза 3, п.2).
7. Проверить соединение на странице состояния проекта Roistat.

## 6. Фаза 3 — выбор схемы и настройка доходности в Roistat

### 6.1 Главное решение: лиды или сделки

Нативная интеграция отслеживает **один** объект. От выбора зависит, откуда Roistat берёт
доход:

| Вариант | Где сумма | Статус | Комментарий |
|---|---|---|---|
| **A. Лиды** (текущая схема) | кастомное поле суммы на лиде, напр. `ufCrmPaymentAmount` (или `ufCrmAmount`) | статус лида | У лидов нет поля «Сумма сделки» (`OPPORTUNITY`), поэтому сумму берём из кастомного поля |
| **B. Сделки** (рекомендуется) | `OPPORTUNITY` (сумма сделки) | статус воронки продаж сделки | Менеджер конвертирует лид в сделку «Создать на основании», доход читается из сделки |

**Рекомендация — вариант B (сделки):** для оплаты брони = выручки это чище: сумма попадает
в `OPPORTUNITY`, а статус воронки сделки напрямую отражает «продано / отказ». Если хочется
минимума переделки — оставайтесь на **варианте A (лиды)**: менять нужно только выбор объекта
и поле суммы в интеграции.

### 6.2 Сопоставление статусов (в настройках интеграции Roistat)

| Статус Битрикс24 | Группа стадий Roistat |
|---|---|
| `NEW` | «В работе» / начало воронки |
| `IN_PROCESS` | «В работе» |
| `PROCESSED` | **«Продажа»** — здесь Roistat фиксирует доход |
| `JUNK` | **«Отказ»** — дохода нет |
| `CONVERTED` | лид переведён в сделку (для варианта B доход идёт из сделки) |

### 6.3 Поле суммы (в настройках интеграции)

- **Вариант A (лиды):** `ufCrmPaymentAmount` (оплачено) или `ufCrmAmount` (стоимость).
- **Вариант B (сделки):** `OPPORTUNITY` (сумма сделки).

Менеджер закрывает заказ со статусом «Продажа» и суммой — данные автоматически уходят в Roistat.

## 7. Фаза 4 — приёмка и запуск в проде

1. Прогнать полный блок тестов из `test-plan.md` на тестовой брони.
2. Убедиться: лид создаётся, `ufCrmRoistat` заполнен, в логе вебхука **нет** строк
   `ROISTAT PROXY REQUEST`.
3. Убедиться в Roistat: визит атрибутирован, при статусе «Продажа» появляется доход по
   источнику, при «Отказ» — визит уходит в отказ без дохода.
4. Убедиться, что на одну броню **одна** карточка (нет дублей).
5. Подключить/проверить товарную аналитику в разрезе номера/комнаты (полнота аналитики).
6. Сообщить менеджерам о новой схеме (лид → сделка «Создать на основании» для варианта B).

**Откат (rollback):** вернуть прежний `litepms-webhook.php` (где была
`maybeSendProxyLead(...)`) и при необходимости вернуть `is_skip_sending` в конфиг, как было.
Нативная интеграция в Roistat остаётся (она безвредна, пока её не отключат).

## 8. Чего НЕ делает этот план (отдельные операции)

- Удаление старых/дублирующихся/тестовых карточек, лидов и сделок — **отдельная операция**,
  выполняется только с явным подтверждением и списком объектов.
- Создание/правка полей и воронки в Битрикс24 (если понадобится добавить UФ-поле или
  стадию) — выполняется отдельно, с показом изменений до применения.
