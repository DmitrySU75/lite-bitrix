# Полный прогон обработчика LitePMS → Bitrix24 (Roistat)

Файлы: `litepms-webhook-fixed.php.txt`, `config.php.txt`.
Дата прогона: 14.10.2026.

> **Важно.** Живой end-to-end прогон из этой среды выполнить невозможно: здесь нет
> PHP-интерпретатора и нет доступа ни к серверу с вебхуком, ни к LitePMS. Поэтому ниже —
> (1) полная матрица сценариев по анализу кода и (2) готовый тест-набор, который вы
> запускаете на своём сервере. Существующие брони тест-набор не затрагивает.

---

## 1. Что делает обработчик по каждому типу события

Диспетчеризация: `switch ($eventType)`.

| # | Событие | Что происходит | Запись в CRM |
|---|---------|----------------|--------------|
| S1 | `new_booking` | Ищет лид по `booking_id`/`user_booking_id`, затем по телефону. Нашёл → обновляет поля (создание). Не нашёл → создаёт новый лид. | Создание/обновление лида |
| S2 | `booking_module`, `channel_manager_booking`, `booking_module_request` | Алиасы `new_booking` — та же ветка. | То же |
| S3 | `edit_booking` | Ищет лид; не нашёл → «NO LEAD, пропуск» (без записи). Нашёл → обновляет поля лида **и** переносит данные на сделку: номер, гости, сумма, оплата, даты, roistat, история; этап сделки при полной оплате/отмене. | Лид + сделка |
| S4 | `edit_booking`, `status_id=3` | То же, что S3, но лид → статус «JUNK», сделка → этап «провалена». | Лид + сделка |
| S5 | `delete_booking` | Принудительно `status_id=3` → ведёт себя как отмена (S4). | Лид + сделка |
| S6 | `booking_module_payment` | Накопление оплаты на лиде (`paid` += разница); при полной оплате статус → обработан; оплата переносится на сделку. | Лид + сделка (оплата) |
| S7 | Повтор события (тот же hash) | Отсекается через файл `.processed` (защита от дублей). | — |
| S8 | Старое событие | Отсекается, если включён `skip_old_bookings` (сейчас выключен). | — |
| S9 | Неизвестный `type` | Лог «UNHANDLED EVENT», без записи. | — |

## 2. Проверка переноса данных в сделку (S3)

На правке брони (`edit_booking`) на сделку пишется **всё** значимое:

- Оплата (`payed`) → поле «Оплачено» на сделке;
- Номер/комната → «Номер» (`UF_CRM_UFCRMROOM`);
- Гости → «Гости» (`UF_CRM_UFCRMGUESTS`);
- Сумма (`price`) → стандартное «Сумма»;
- Даты заезда/выезда;
- roistat-визит;
- строка истории брони (дозаписывается без дублей);
- этап: полная оплата → «Сделка успешна», отмена → «Сделка провалена» (если заданы `stage_paid`/`stage_cancelled`).

Сделка ищется: сначала по roistat-визиту, затем (если визит пуст) по номеру брони
в «Истории брони» — правки с пустым визитом больше не пропускаются.

## 3. Исправление в этой версии (правка от 14.10)

**Платёж с пустым roistat не достигал сделки.** `updateDealPayment` искал сделку только
по визиту и при пустом визите просто пропускал событие — оплата не появлялась на
карточке сделки и не попадала в аналитику. Добавлен запасной поиск по номеру брони
(та же логика, что в `edit_booking`). Теперь платёж находится на сделке и по номеру брони.

## 4. Защита «не затирать вручную заполненный контакт»

- Существующие телефон и почта в карточке **всегда** сохраняются.
- Из вебхука добавляются только те значения, которых ещё нет (с нормализацией,
  чтобы не плодить дубли вида `7926…`/`+7926…`).
- Некорректные значения отсекаются `sanitizePhone`/`sanitizeEmail`.

## 5. Тест-набор (запускать на своём сервере)

Вебхук принимает `application/x-www-form-urlencoded` (как `/updateBooking` LitePMS).
Все тесты используют **синтетический** `booking_id` (99xxx), которого нет в базе, —
существующие брони и сделки не затрагиваются.

### 5.0 Безопасный режим

Перед прогоном **создающих** веток поставьте в `config.php`:

```php
'dry_run' => true,
```

В этом режиме обработчик логирует «would…» и **ничего не пишет** в CRM.
Тесты, помеченные «без записи», безопасны и при `dry_run=false`.

### 5.1 Прогон без записи (несовпадающий booking_id)

Эти запросы проверяют ветки «лид не найден → пропуск» — безопасны в любом режиме:

```bash
URL='https://ВАШ_СЕРВЕР/litepms-webhook.php'

# S3 — правка брони (лида нет → NO LEAD, пропуск)
curl -s "$URL" --data-urlencode 'type=edit_booking' \
  --data-urlencode 'booking_id=99001' \
  --data-urlencode 'user_booking_id=99001' \
  --data-urlencode 'status_id=2' \
  --data-urlencode 'price=8000' \
  --data-urlencode 'payed=8000' \
  --data-urlencode 'date_in=2026-12-01 14:00:00' \
  --data-urlencode 'date_out=2026-12-05 12:00:00' \
  --data-urlencode 'room_name=311' \
  --data-urlencode 'person=2'

# S5 — удаление брони (лида нет → пропуск)
curl -s "$URL" --data-urlencode 'type=delete_booking' \
  --data-urlencode 'booking_id=99002' \
  --data-urlencode 'status_id=3'

# S6 — платёж (лида нет → пропуск)
curl -s "$URL" --data-urlencode 'type=booking_module_payment' \
  --data-urlencode 'booking_id=99003' \
  --data-urlencode 'price=3000'

# S9 — неизвестный тип (UNHANDLED EVENT)
curl -s "$URL" --data-urlencode 'type=unknown_event' \
  --data-urlencode 'booking_id=99004'
```

Ожидание в логе: `NO LEAD … — пропуск, лид не создаётся` / `UNHANDLED EVENT`.
Никаких записей в CRM не произойдёт.

### 5.2 Полный write-сценарий (обязательно `dry_run=true`)

Полная проверка создания лида и переноса в сделку требует **нового** тестового события
(не существующей брони). Прогон создания лида:

```bash
# S1 — создание лида из новой брони (dry_run=true → только лог)
curl -s "$URL" --data-urlencode 'type=new_booking' \
  --data-urlencode 'booking_id=99100' \
  --data-urlencode 'user_booking_id=99100' \
  --data-urlencode 'status_id=1' \
  --data-urlencode 'price=12000' \
  --data-urlencode 'payed=0' \
  --data-urlencode 'client_name=Тест' \
  --data-urlencode 'client_surname=Прогон' \
  --data-urlencode 'client_phone=+79990000001' \
  --data-urlencode 'date_in=2026-12-10 14:00:00' \
  --data-urlencode 'date_out=2026-12-15 12:00:00' \
  --data-urlencode 'room_name=315 (1 этаж)' \
  --data-urlencode 'person=2' \
  --data-urlencode 'roistat=test-visit-99100'
```

Ожидание в режиме dry-run: лог `DRY RUN: would create lead`.

### 5.3 Что проверить по логу после боевого события

После установки файлов на сервер откройте реальную правку **новой** тестовой брони и
сверьте лог:

- `LEAD BOOKING FIELDS UPDATED …` — поля лида;
- `DEAL UPDATE OK deal …` — сделка получила номер/гостей/сумму/оплату/roistat;
- `DEAL PAYMENT UPDATED …` — оплата дошла до сделки;
- `STATUS: full payment … → PROCESSED` — статус лида (при полной оплате);
- `NAME KEPT (manual edit)` — имя не затёрто;
- `PRICE KEPT (manual edit)` — сумма не затёрта;
- контакт `fm` — телефон/почта не заменились, только добавились новые.

По каждой строке `[DONE] … status=success` — событие отработало без ошибок.

## 6. Ограничения, которые стоит держать в голове

- Проверить синтаксис PHP (`php -l`) в этой среде нельзя — PHP здесь не установлен.
  Перед выкладкой прогоните `php -l litepms-webhook.php && php -l config.php` на сервере.
- В режиме `dry_run` обработчик логирует «would…» и не выполняет сами чтения/записи,
  поэтому полную траекторию write-ветки в dry-run увидеть нельзя — она проверяется
  только на реальном (новом) тестовом событии.
- `booking_module_payment` не трогает номер, гостей и историю на лиде — только оплату.
  Это ожидаемое поведение: остальные поля приходят через `edit_booking`.
