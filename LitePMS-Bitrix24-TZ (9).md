# Техническое задание

## Интеграция системы бронирования LitePMS с лидами Bitrix24 (CRM как агрегатор)

**Версия:** 1.2 (финальная, для согласования с заказчиком)
**Дата:** 30 сентября 2026

---

## 1. Цель и назначение

Создать приложение (интеграционный адаптер), которое обеспечивает автоматическую загрузку данных о бронированиях из системы **LitePMS** в модуль **CRM (лиды)** Bitrix24. CRM используется как **агрегатор всех заявок и броней** — единая аналитическая картина по гостю, заказу и рекламному источнику; фактические данные и обработка бронирований ведутся на стороне Bitrix. 

**Уточнение по характеру обмена (подтверждено на текущем этапе):**
- **Направление A — LitePMS → Bitrix24 (автоматическое):** новая бронь в LitePMS автоматически превращается в лид в CRM, а последующие изменения брони (статус, даты, сумма, гость, атрибуция) синхронизируются в соответствующий лид через исходящие вебхуки LitePMS.
- **Направление B — Bitrix24 → LitePMS (статус и данные брони):** у LitePMS **есть** REST-API с методом `POST /updateBooking` (авторизация по `login`+`hash`), который позволяет **обновлять статус брони** (`status_id`) и другие поля брони/клиента. Поэтому изменения стадии, внесённые в CRM, технически **можно передавать обратно в LitePMS** — обратный канал для статуса существует (см. п. 8.4, 7.1).

Итоговая цель — полный и актуальный срез всех заявок и броней в CRM для отчётности, контроля и сквозной аналитики, с согласованным владельцем статуса по гибридной схеме (до порога — LitePMS, после порога — CRM с опциональной записью статуса обратно в LitePMS через `updateBooking`).

**Гибридная схема владения статусом (уточнение):** до достижения порогового события/стадии воронки статус лида ведёт **LitePMS** (вебхуки двигают лид по воронке автоматически). После достижения порога сотрудники переводят лид в Bitrix24 **вручную**, а статус (по согласованному правилу) либо остаётся только в CRM, либо дополнительно записывается обратно в LitePMS через `POST /updateBooking`. Остальные поля (даты, сумму, оплату, атрибуцию, комментарий) адаптер синхронизирует всегда. Подробнее — п. 7.1, 8.4 и 10.3.

## 2. Область (scope)

### Входит в объём
- Приём и обработка исходящих вебхуков LitePMS (события по броням, оплатам, предзаявкам).
- Создание лидов в Bitrix24 и обновление их полей по данным пакета (payload) LitePMS.
- Маппинг полей «LitePMS → лид Bitrix24».
- Установка и поддержание связи «бронь ↔ лид» через внешний идентификатор (UKEY/EXT ID).
- Дедупликация и идемпотентность (защита от зацикливания и дублей).
- Логирование, обработка ошибок, очередь и повторные попытки.
- Передача данных атрибуции (источник/канал, UTM) в лиды для **сквозной аналитики Bitrix24** (см. п. 14).

### Вне объёма (на текущем этапе)
- Автоматическое создание брони из лида в LitePMS — **не выполняется** (метод `createBooking`, при необходимости, выносится в отдельный этап).
- Передача из CRM в LitePMS **коммерческих и клиентских полей**, кроме статуса — **по согласованию**; по умолчанию обратно передаётся только статус брони (`updateBooking` → `status_id`), остальные поля ведёт LitePMS.
- Полная синхронизация истории БД LitePMS в CRM (одноразовый импорт) — выносится в отдельный этап.
- Интеграция с другими модулями CRM (контакты, сделки, компании), кроме лидов.
- Доработка самого LitePMS (используется штатный API/вебхуки системы).

## 3. Архитектура

Рекомендуемая схема — **прокси-приложение (адаптер)**, размещённое на отдельном сервере/хостинге, которое выступает посредником между LitePMS и Bitrix24.

```
                    (исходящие вебхуки, POST)
LitePMS  --(webhook, POST)-->  [ Адаптер (наш сервис) ]  --(REST, лиды)-->  Bitrix24
    ^                                |  |
    |___(updateBooking, POST)________/  +---> База состояния/очередь + логи
        (обратный канал статуса, п. 8.4)
```

> Обмен **двусторонний по статусу**: направление A (LitePMS → Bitrix24) через исходящие вебхуки, направление B (Bitrix24 → LitePMS, только статус) через `POST /updateBooking` с API-ключом. Остальные поля остаются однонаправленными (LitePMS → CRM), см. п. 4.2 и 8.4.

### Почему нужен адаптер, а не прямая связь «LitePMS → Bitrix24»
- У двух систем разные модели данных и форматы — нужна **трансляция и маппинг**.
- Нужна **связка брони и лида** (ведение пары идентификаторов).
- Нужны **очередь, ретраи, дедупликация и логирование**, которых нет «из коробки».
- Адаптер скрывает от LitePMS особенности REST Bitrix24 и наоборот.

> **Решение принято:** технологический стек адаптера — **PHP** (с REST-клиентом, очередью и фоновыми задачами). Логика настоящего ТЗ от конкретного языка не зависит: при реализации на PHP применяется она же.

## 4. Потоки данных

### 4.1. Направление A: LitePMS → Bitrix24 (создание и обновление лида)

**Триггеры (события LitePMS — уточнить фактический список в документации LitePMS):**
- создание новой брони;
- изменение статуса брони (подтверждена / отменена / оплачена / заселение / выселение и т.п.);
- изменение дат заезда/выезда, количества гостей, суммы, номера;
- изменение данных гостя.

**Действия адаптера:**
1. Принять входящий вебхук LitePMS, проверить подпись/секрет.
2. Извлечь ключ брони (ID брони в LitePMS) и тип события.
3. Определить, существует ли уже сопоставленный лид (см. п. 6 «Связка идентификаторов»).
4. Если лида нет и событие = «создание» → **создать лид** (`crm.lead.add`) с маппингом полей.
5. Если лид есть → **обновить поля лида** (`crm.lead.update`).
6. Записать результат в лог и состояние.
7. Передать в лид данные атрибуции (источник/канал, UTM — при наличии в данных LitePMS) для сквозной аналитики (см. п. 14).

### 4.2. Направление B: Bitrix24 → LitePMS (статус брони)

**Уточнение архитектуры (подтверждено): у LitePMS есть REST-API с методом `POST /updateBooking`** (авторизация `login`+`hash`), которым можно обновлять бронь, включая поле **`status_id`** (статус брони) и данные брони/клиента (см. п. 8.4).

В рамках гибридной схемы (см. п. 1, 7.1) обратный канал используется **только для статуса брони** и только по согласованному правилу (после порога). Следствия:
- **лид не создаёт бронь** в LitePMS (`createBooking` не используется);
- из CRM в LitePMS передаётся **только статус** (`updateBooking` → `status_id`); остальные поля брони (даты, суммы, клиент) ведёт LitePMS; оценка и ответственный менеджер — атрибуты лида, в LitePMS не передаются;
- обработчик `crm.lead.onUpdate` (направление B по статусу) **включается** в схему адаптера: при изменении стадии лида адаптер определяет бронь по `EXT_ID` и вызывает `POST /updateBooking`.

> **Правило статуса (гибрид, п. 7.1):** если лид ещё не достиг целевой стадии — статус ведёт LitePMS (LitePMS → CRM); вебхуки LitePMS остаются единственным источником. После достижения порога статус ведут сотрудники в CRM, а адаптер **опционально записывает его обратно в LitePMS** через `updateBooking`. Точное правило (писать ли статус обратно после порога и для какого диапазона стадий) — согласовывается с заказчиком (см. п. 16).

CRM остаётся **агрегатором** всех заявок и броней; фактическая обработка (даты, финансы, гости) ведётся в LitePMS, а статус после порога — согласованно в обеих системах.

## 6. Связка идентификаторов «бронь ↔ лид»

Чтобы знать, какая бронь соответствует какому лиду, вводится **пара идентификаторов**:
- `LitePMS booking ID` — уникальный ID брони в LitePMS;
- `CRM lead ID` — уникальный ID лида в Bitrix24.

**Правила:**
1. При первом создании лида из брони в поле лида `EXT_ID` (специальное пользовательское поле типа «строка») записывается `booking_id` из LitePMS.
2. При обратном запросе (из LitePMS) поиск лида ведётся по этому полю (`crm.lead.list` c фильтром по `EXT_ID`).
3. Хранение обратной ссылки (`lead_id` в LitePMS) — **выполняется** через REST-метод `POST /updateBooking`: `lead_id` записывается в поле `client_extradata` брони (см. п. 8.4). Это позволяет при изменении стадии лида в CRM (направление B) точно определить броню в LitePMS.
4. Сопоставление считается биективным: одна бронь ↔ один лид.

**Если связка не найдена** — создаётся новый лид (с доп. проверками по уникальности, см. п. 9).

## 7. Правила синхронизации и приоритет источника

Чтобы избежать конфликтов, необходимо зафиксировать **политику «кто главный» по группам полей**:

| Группа полей | Источник-владелец | Обоснование |
|--------------|-------------------|-------------|
| Даты заезда/выезда, номер, число гостей | LitePMS | PMS — источник фактического бронирования |
| Финансы (сумма, статус оплаты) | LitePMS | деньги считаются в PMS |
| Канал/источник | LitePMS | источник брони |
| Стадия воронки лида | **гибрид** (см. ниже) | до порога — LitePMS, после порога — Bitrix24 |
| Оценка, ответственный менеджер | Bitrix24 | объект CRM, ведётся сотрудниками в CRM |
| Контактные данные гостя | LitePMS (приоритет) | избегаем затирания актуального телефона |

### 7.1. Гибридная схема владения статусом (порог «заморозки»)

Стадия лида управляется последовательно — сначала LitePMS, затем Bitrix24. Переключатель — **пороговое событие** (целевая стадия воронки), задаётся в конфигурации **отдельно для каждой воронки** (B2B и Частные).

**До порога** (лид ещё не достиг целевой стадии воронки):
- LitePMS — владелец статуса;
- адаптер при каждом событии вебхука считывает текущую стадию лида (`crm.lead.get`) и, только если лид **ещё не достиг порога**, переводит его по карте статусов (см. п. 10.3).

**После порога** (лид достиг/прошёл целевую стадию воронки):
- статус ведут **сотрудники в CRM вручную** — адаптер больше **не перезаписывает** поле статуса вебхуками LitePMS;
- адаптер продолжает синхронизировать **все остальные поля** (даты, сумму, оплату, атрибуцию, комментарий, контактные данные);
- по согласованному правилу изменение стадии в CRM **опционально записывается обратно в LitePMS** через `POST /updateBooking` → `status_id` (см. п. 8.4), чтобы статусы в обеих системах оставались в синхроне;
- сам факт того, что статус «заморожен» для вебхуков LitePMS, фиксируется в логе.

**Правила и оговорки:**
1. **Порог необратим:** после его достижения вебхуки LitePMS статус лида не меняют (защита ручной работы менеджера от «перезаписи» пакетом PMS).
2. **Обратный канал статуса существует** (`POST /updateBooking`), но используется **только по согласованному правилу** — по умолчанию передаётся только `status_id`, остальные поля брони ведёт LitePMS. Если обратная запись статуса не включена, статусы после порога **могут расходиться** — это ожидаемое поведение, фиксируется в логе.
3. **Конфигурация порога:** для каждой воронки задаётся код целевой стадии (например, «Подтверждено → Бронирование» для B2B). Точные значения — по результатам согласования (см. п. 16).
4. **Сравнение значений:** адаптер обновляет лид только при фактическом изменении данных; если поле уже равно значению из вебхука — пропуск (исключает лишние записи и зацикливание, см. п. 9.2). То же правило действует для записи статуса в LitePMS: если `status_id` в LitePMS уже совпадает с изменением из CRM — `updateBooking` не вызывается.

**Реализация (адаптер), направление A:** перед записью статуса адаптер выполняет чтение текущего лида (`crm.lead.get`), сверяет достигнутый лидом порог по справочнику конфигурации и, если порог пройден, исключает поле стадии из пакета обновления, сохраняя остальные поля.

**Реализация (адаптер), направление B:** обработчик `crm.lead.onUpdate` ловит смену стадии лида после порога, по `EXT_ID`/`lead_id` находит броню в LitePMS и вызывает `POST /updateBooking` с новым `status_id` (при включённой функции и фактическом изменении).

Оценка и ответственный менеджер всегда ведутся в CRM и никогда не перезаписываются адаптером; в LitePMS они не передаются.

Двойное поле, изменённое в обеих системах одновременно, решается по указанному владельцу; расхождение фиксируется в логе.

## 8. Техническая реализация каналов

### 8.1. Входящий вебхук Bitrix24 (есть у заказчика)

Администратор портала выпускает **входящий REST-вебхук** со следующими правами (scope):
- `crm` (обязательно) — для работы с лидами;
- `user` — для получения данных о менеджерах (опционально).

Адаптер хранит URL вебхука (вида `https://<портал>/rest/<user_id>/<токен>/`) как секрет в конфигурации **и не передаёт его никуда**, кроме запросов адаптера к порталу.

**Основные методы (в рамках данного ТЗ):**
- `crm.lead.add` — создание лида;
- `crm.lead.update` — обновление лида;
- `crm.lead.get` — чтение лида по ID;
- `crm.lead.list` — поиск лидов (по `EXT_ID`, по контактам);
- `crm.lead.fields` — получение перечня и кодов полей лида (для проверки маппинга).

### 8.2. Исходящий вебхук (обработчик событий) Bitrix24

Обработчик событий `crm.lead.onUpdate` используется для **направления B (статус)**: при смене стадии лида после порога (см. п. 7.1) адаптер вызывает `POST /updateBooking` в LitePMS с новым `status_id`. Функция включается конфигурацией (per-funnel threshold; опциональный обратный канал). `crm.lead.onAdd` в схеме не используется — лид не создаёт броню.

### 8.3. Каналы и API LitePMS

Документация Lite PMS предоставлена заказчиком (ссылка: `https://litepms.ru/welcome/help?id=103`).

- **API-ключ** обязателен для любых обращений к API Lite PMS; доступен только на тарифе **Business** и выдаётся по запросу в службу поддержки.
- Официальная **документация REST-API** (создание/поиск бронирований, работа с клиентами, тарифами и т.п.) предоставляется по запросу вместе с ключом.
- **Универсальный API Connector** — если нужного события нет в готовом наборе, используется «Входящий веб-хук» с привязкой логики к полю, приходящему в запросе.
- **Модуль бронирования** имеет собственный API: в запросах указываются ID пользователя, категории или номера.

#### 8.3.1. Доставка уведомлений

- **Подтверждённая конфигурация в LitePMS:** webhook-уведомления включены (`да`), адрес для уведомлений — `https://avshotel.ru/include/...php` (секретный, непубликуемый). Включены следующие уведомления:
  - при создании брони вручную;
  - при изменении брони;
  - при создании брони через модуль бронирования;
  - при удалении брони;
  - при создании предварительной заявки на бронь;
  - при поступлении брони через каналы продаж;
  - при поступлении онлайн-платежа;
  - при достижении целей счётчика посещений в модуле бронирования.
- Уведомления отправляются на указанный в настройках адрес **методом POST**.
- Если адрес недоступен (сервер не возвращает код `200`) — уведомления **могут быть заблокированы**. Это обязательное требование к надёжности endpoint адаптера (см. п. 12).
- **Подпись/секрет вебхука не предусмотрена** — документация описывает простой POST без HMAC-подписи. Включённый адрес уведомлений (`https://avshotel.ru/include/...php`) должен быть секретным и не публиковаться; безопасность обеспечивается на стороне адаптера (см. п. 11).
- **Лимиты запросов (rate limits) документацией не установлены.**

#### 8.3.2. Поддерживаемые события

- создание брони вручную;
- изменение брони;
- создание брони через модуль бронирования;
- удаление брони;
- создание предварительной заявки на бронь;
- поступление брони через каналы продаж;
- поступление онлайн-платежа;
- достижение целей счётчика посещений в модуле бронирования.

## 8.4. REST-API LitePMS (направление B и чтение броней)

У LitePMS **есть** HTTP REST-API (базовый адрес — `https://litepms.ru/api`, подтверждён заказчиком). Авторизация для всех запросов — параметры **`login`** (логин пользователя) и **`hash`** (API-ключ), передаваемые в строке запроса (query). Доступен на тарифе **Business**.

Доступные методы (по документации API):

| Метод | Тип | Назначение |
|-------|-----|------------|
| `/getBookingFields` | GET | поля, используемые в бронировании |

| `/getBooking` | GET | информация о конкретном бронировании |
| `/createBooking` | POST | создание бронирования |
| `/updateBooking` | POST | **обновление брони и клиента (в т.ч. статуса)** |

| `/addBookingService` | POST | добавление услуги к бронированию |
| `/searchBooking` | POST | поиск броней по параметрам |

**Метод `POST /updateBooking`** — обратный канал для статуса (направление B). Формат — `application/x-www-form-urlencoded`, обязательный параметр **`id`** (ID брони). Ключевые поля:

| Параметр | Описание |
|----------|----------|
| `id` *(обязателен)* | ID брони |

| `client_extradata` | Доп. данные клиента — используется адаптером для хранения `lead_id` (см. п. 6) |

| `time_in`, `time_out` | Время заезда / выезда (`ЧЧ:ММ`) |
| `person`, `person_add` | Количество основных / доп. мест |
| `room_id`, `bed_id`, `is_bed` | Номер, спальное место, признак спального места |
| `price`, `stayprice`, `stayprice_type` | Стоимость / своя цена и её тип |
| `rate_id`, `label_id`, `service_id`, `service_number` | Тариф, метка, источник бронирования, номер у источника |
| `client_name`, `client_surname`, `client_middlename`, `client_phone`, `client_email`, `client_address`, `client_comment`, `client_birthday`, `client_doc_series`, `client_doc_code`, `client_doc_when`, `client_doc_where`, `client_gender` | Данные клиента |

> Адаптер в рамках гибридной схемы использует `updateBooking` **только** для записи статуса (`status_id`) и сохранения обратной ссылки `lead_id` (`client_extradata`). Остальные поля брони остаются под управлением LitePMS (см. п. 4.2, 7.1).

## 9. Дедупликация, идемпотентность и защита от зацикливания

### 9.1. Идемпотентность
Каждое событие обрабатывается **ровно один раз** на уровне приложения. Для этого:
- адаптер хранит `event_id`/хэш полученного сообщения и не обрабатывает повторно уже обработанный (`idempotency key`);
- все запросы к Bitrix24 (создание лида) защищены от дублей проверкой `EXT_ID` перед созданием.

### 9.2. Защита от зацикливания «пинг-понга»
Типичная проблема двусторонней синхронизации — бесконечный обмен уведомлениями, когда изменение из системы A вызывает событие в системе B, которое снова уходит в A.

**Меры:**
1. **Тэг происхождения:** при записи поля в Bitrix24, сделанной самим адаптером, проставляется служебная пометка (например, в поле/комментарии источника), а обработчик `onUpdate` игнорирует события, порождённые самим адаптером.
2. **Сравнение значений:** обработчик обновляет объект только при фактическом изменении данных («поле в лиде уже равно значению из мяча LitePMS — пропускаем»).
3. **Глубина/флаг обработки:** признак «последняя запись сделана адаптером» хранится в состоянии и снимается при новом изменении из PMS/CRM.
4. **Обратный канал (направление B):** запись статуса в LitePMS через `updateBooking` не порождает нового обработчика, моделирующего ответ — событие, порождённое самим адаптером (повторный вебхук изменённой брони с совпадающим `status_id`), игнорируется по правилу «сравнения значений» (см. также п. 7.1).

### 9.3. Дедупликация лидов
Перед созданием нового лида из брони выполняются проверки:
- поиск по `EXT_ID` (та же бронь) — если найден, обновляем, а не создаём;
- при отсутствии `EXT_ID` — поиск по телефону/email гостя + датам (эвристика) с выводом в лог возможного дубля.

## 10. Обработка ошибок, очередь и логирование

### 10.1. Очередь и повторные попытки
- Все входящие события помещаются в **очередь** (в памяти сервиса или в БД/брокере).
- При сбое (сеть, лимит, невалидный payload) — **повторные попытки по экспоненциальной схеме** (например, 3–5 попыток с возрастающей задержкой).
- При устойчивом сбое событие помечается как «ошибка» для ручного разбора.

### 10.2. Логирование
- Фиксируются: полученные события, решения (создан/обновлён/пропущен), ответы портала, ошибки и временные метки.
- Лог не должен содержать чувствительные данные дольше, чем требуется (телефоны/email логируются частично или маскируются).
- Отчётность по синхронизации (журнал событий, ошибки, результаты) выгружается в формате **XLS** — выгружаемые отчёты доступны по периодам.

### 10.3. Справочники статусов
Составляется **таблица соответствия статусов**: «`status_id` LitePMS ↔ стадии воронки лида Bitrix24». Коды LitePMS (см. п. 8.3.3): 1 — не подтверждено, 2 — подтверждено, 3 — отменено, 4 — выезд, 5 — незаезд, 6 — проживание, 8 — резерв, 9 — overbooking. Пример (заполняется по факту):

В портале используются **две воронки**: для частных клиентов (B2C) и для B2B. Признак разделения задаётся в конфигурации по справочнику LitePMS: «Групповой заезд» → воронка B2B; «Индивидуальный заезд», «Блоггеры» → воронка Частных (B2C); **по умолчанию** все брони — в Частные.

**Воронка B2B** (источник «Групповой заезд»):

| `status_id` LitePMS | Стадия воронки Bitrix24 |
|---------------------|--------------------------|
| 1 — не подтверждено | Разобрать / Первичный звонок / Разговор с ЛПР / КП / Звонок и ОС / Встреча |
| 2 — подтверждено | Бронирование / Договор+Счет / Авансы / Корректировка количества / Расчет |
| 6 — проживание | Заезд |
| 4 — выезд | Акты и ОС / Сделка успешна |
| 5 — незаезд | Сделка провалена |
| 3 — отменено | Сделка провалена |
| 8 — резерв | *(стадия не меняется)* |
| 9 — overbooking | Сделка провалена |

**Воронка Частных (B2C):** справочник стадий на согласовании с заказчиком (см. п. 16).

**Обратный маппинг (направление B):** для записи статуса из CRM в LitePMS используется **обратная таблица** «стадия воронки Bitrix24 → `status_id` LitePMS» (инверсия прямой карты выше, по каждой воронке отдельно). Применяется только после порога «заморозки» и по согласованному правилу (см. п. 7.1, 16).

**Порог «заморозки» статуса (гибрид):** указывается для каждой воронки отдельно (например, для B2B — достижение стадии «Бронирование» или «Заезд»; точное значение подтверждается заказчиком). До порога статусом управляет LitePMS, после — только CRM (см. п. 7.1).

Парное правило по оплате: событие `booking_module_payment` не двигает стадию воронки, а отражается в полях оплаты лида (сумма, дата, статус оплаты).

## 11. Безопасность

- Обмен только по **HTTPS**.
- **Секреты** (токен входящего вебхука Bitrix24, API-ключ LitePMS, секрет подписи) хранятся в защищённом конфиге/хранилище секретов и **никогда** не попадают в код, логи или репозиторий.
- **Вебхуки LitePMS не подписываются** (HMAC не предусмотрен): endpoint адаптера должен быть на секретном, непубликуемом адресе, принимать только от настроенного источника и дополнительно проверять источник по фиксированному секретному ключу/заголовку (см. п. 8.3.1).
- Обработчик Bitrix24: при возможности — проверка подписи события.
- Валидация и санитизация всех входящих данных (защита от инъекций и некорректного payload).
- Разграничение прав: приложению выдаётся минимально необходимый скоуп.

## 13. Сценарии и приёмочные критерии

### 13.1. Ключевые сценарии для проверки
1. **Новая бронь в LitePMS** → создан лид с корректными полями и `EXT_ID = booking_id`.
2. **Изменение статуса брони в LitePMS** → обновлён соответствующий лид.
3. **Создан лид в CRM** → новая броня в LitePMS **не создаётся** (метод `createBooking` вне объёма, см. п. 2), однако **статус** лида после порога может записываться обратно в броню LitePMS через `POST /updateBooking` (направление B, см. п. 7.1 и 8.4). Прочие поля лида, изменённые вручную в CRM, в LitePMS не передаются — их владельцем остаётся LitePMS.
4. **Смена стадии/ответственного в LitePMS** → соответствующая стадия лида обновлена в CRM (направление A).
5. **Дубль вебхука** (повтор события) → не создаёт второй лид и не накапливает дубли.
6. **Разрыв сети/ошибка** → событие уходит в очередь и повторяется, система приходит в консистентное состояние.
7. **Оплата брони** (`booking_module_payment`) → в лиде отражена отметка/сумма оплаты (для сквозной аналитики, см. п. 14).
8. **Гибрид — до порога:** броня двигает лид по установленной воронке автоматически (например, B2B «Неподтверждено» → «Подтверждено» → … → «Заезд») по карте статусов.
9. **Гибрид — после порога:** когда лид достиг целевой стадии воронки, приходящее изменение статуса из LitePMS **не перезаписывает** стадию лида, но остальные поля (даты, сумма, оплата, атрибуция, комментарий) обновляются.
10. **Ручная работа менеджера в CRM:** перевод лида менеджером в любую стадию после порога сохраняется и не откатывается при поступлении вебхука LitePMS.
11. **Расхождение статусов:** до порога статус в LitePMS и в CRM синхронизирован; после порога статус ведёт CRM, и при включённой обратной записи он передаётся в LitePMS через `updateBooking`. Если обратная запись отключена или не согласована для конкретной воронки, после порога статусы могут расходиться — это не считается ошибкой, фиксируется в логе.

### 13.2. Критерии приёмки
- Все сценарии п. 13.1 выполняются без ручного вмешательства.
- Максимальная задержка синхронизации (от события до отражения в другой системе) — **не более 5 минут** (SLA).
- Лог по каждому событию доступен и читаем.
- Секреты не появляются в логировании.
- Документация по маппингу и запуску системы в комплекте.

## 14. Сквозная аналитика в Bitrix24

Сквозная аналитика собирает данные о рекламных расходах и о том, какие из них привели к клиентам в CRM. Она показывает **полный путь клиента** — от клика по рекламному объявлению до брони и оплаты — и позволяет рассчитывать **стоимость привлечения клиента** и **ROI** по рекламным каналам. В рамках данной интеграции это означает атрибуцию «реклама/сайт → лид → бронь в LitePMS → оплата».

### 14.1. Требование к тарифу
- Функция доступна не на всех тарифах (например, входит в тариф «Профессиональный»). Необходимо подтвердить её наличие на текущем тарифе портала администратором.

### 14.2. Настройка в Bitrix24 (выполняется администратором портала)
- **Подключение источников трафика:** CRM → Аналитика → Сквозная аналитика → Настройки подключения → Подключение источников трафика; добавить источник (ВКонтакте, Google Ads и др.) и задать UTM-метку.
- **Настройка UTM-меток** для каждого источника (`utm_source`, `utm_medium`, `utm_campaign`).
- **Распределение телефонов и e-mail** для атрибуции заявок по источникам (если заявки принимаются по этим каналам).
- **Отчёты:** CRM → Аналитика → Оперативная аналитика → Сквозная аналитика → Отчёты (например, «Окупаемость рекламы»).

### 14.3. Требования к адаптеру
- При создании/обновлении лида из брони LitePMS адаптер передаёт **источник/канал брони** в поле лида `SOURCE_ID` (маппинг каналов LitePMS → справочник источников CRM, см. п. 5).
- Полезная нагрузка вебхука LitePMS содержит атрибуционные параметры `ym_clid` (ClientID Яндекс.Метрики), `etext` и `yclid` (рекламные параметры) — адаптер передаёт их в соответствующие пользовательские поля лида (UTM/tracking), чтобы в CRM сформировался корректный **«Путь клиента»** (реклама → сайт → бронь → лид).
- Конверсия в сквозной аналитике должна учитывать переход брони в **оплату**: фиксируются момент и сумма оплаты (связка по `EXT_ID` и статусам оплаты из LitePMS, см. п. 7 и 10.3).
- Если источник в данных LitePMS не распознан — логируется как «без источника» для ручного маппинга.

### 14.4. Критерий приёмки
- В отчётах сквозной аналитики прослеживается атрибуция «источник → лид → бронь → оплата», доступны стоимость привлечения и ROI по каналам.

## 15. Этапы разработки

1. **Сбор входных данных:** документация LitePMS (вебхуки, API, статусы), фактические коды полей лида и UF портала.
2. **Согласование маппинга** и политики владения полями, справочников статусов.
3. **Каркас адаптера:** приём вебхуков, очередь, логирование, связка идентификаторов.

6. **Сквозная аналитика:** настройка источников трафика в Bitrix24 и передача атрибуции (источник/UTM) из адаптера (см. п. 14).
7. **Обработка ошибок, ретраи, защита от зацикливания.**
8. **Тестирование сценариев (п. 13) и приёмка.**
9. **Развёртывание, мониторинг, документация.**

## 16. Что требуется от заказчика для продолжения

1. Документация и формат уведомлений **LitePMS** получены (см. п. 8.3); подтверждены **отсутствие подписи вебхука (HMAC)** и **rate limits не установлены**. **Входящий REST-API у LitePMS есть** — метод `POST /updateBooking` (см. п. 8.4) используется для направления B (статус брони). **Осталось подтвердить:** реальные значения **`login`/`hash`** (API-ключ), точную схему авторизации и согласованное правило обратной записи статуса по воронкам (см. п. 7.1, 10.3).

4. Список **статусов броней LitePMS** и желаемые соответствия **стадиям воронки лидов**.

   - карта стадий **воронки Частных (B2C)** — соответствие `status_id` LitePMS → стадии воронки;

   - подтверждение справочника источников (маппинг «Групповой заезд / Индивидуальный заезд / Блоггеры» и других «Источников бронирования» LitePMS → источники лидов в CRM).

## 17. Принятые решения (закрытые вопросы)

| Вопрос | Решение |
|--------|---------|
| Технологический стек адаптера | **PHP** |
| Политика владения полями (п. 7) | **подтверждена** |
| Роль CRM | **агрегатор** всех заявок/броней; обработка в LitePMS |
| Владение статусом лида | **гибридная схема (п. 7.1):** до целевой стадии статус ведёт LitePMS, после — только CRM (адаптер статус не перезаписывает, остальные поля синхронизирует) |
| Направление B (лид → LitePMS) | **статус через `POST /updateBooking`** (после порога, по согласованному правилу воронок); остальные поля не передаются |
| Автосоздание/обновление брони из лида | **не выполняется** (метод `createBooking` вне объёма); пишется только `status_id` и `lead_id` в `client_extradata` |
| Формат отчётности/логов | **XLS** |
| SLA задержки синхронизации | **не более 5 минут** |
| Подпись/секрет вебхука LitePMS (HMAC) | **не предусмотрена** — безопасность на стороне адаптера (п. 8.3.1, 11) |
| Лимиты запросов LitePMS (rate limits) | **не установлены** |
| Форматы уведомлений LitePMS (п. 8.3.3–8.3.5) | **зафиксированы** (бронь / оплата / предзаявка) |
| Воронки сегментации (п. 10.3) | **две:** Частные (B2C) и B2B; признак — справочник LitePMS («Групповой заезд» → B2B, остальное → Частные, по умолчанию Частные) |
